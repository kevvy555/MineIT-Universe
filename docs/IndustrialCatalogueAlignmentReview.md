The alignment gives `machine.partIds` one precise meaning: it is the unique projection of `servicePartRequirements`. `manufacturing.finishedPartInputs` remains the production BOM for one Machine. Every finished Part input now resolves to a service slot; the two fields no longer compete as vague component lists. Building `machineIds` is likewise a compatibility index, while `equipmentConfigurations` owns required, conditional, optional and alternative fit-outs with per-level quantities.

One coherent deterministic wear model now spans Parts, Machines and Buildings. Universe owns parameters and compatibility; a game save owns Machine instances, installed Part instances, condition, hours, intensity and repair history. Buildings do not receive a competing wear counter: their output and capability derive from their operational installed Machines.

Wear formula: `nextConditionPct = clamp(conditionPct - baseWearRatePctPerEquivalentFullLoadHour * operatingHours * pow(intensity, intensityExponent), 0, 100)`. Machine condition is the weighted mean of service-slot condition using conditionWeight; performanceFactor = machineConditionPct / 100 while powered, enabled and without a failed critical service slot; otherwise 0. Any critical slot at or below its Part failureConditionPct disables the Machine.

## G — Android integration impact

Android should extend its unified Universe build-time bundle with derived `buildings`, `machines`, `parts` and `industrialSpecifications` snapshots from one immutable Universe commit. These remain generated bundle outputs with shared source/schema/content provenance; Android must not author a second catalogue. Runtime models should reference canonical Building, Machine, Part and capability-configuration IDs, while save-owned instances use their own persistent instance IDs.

For a newly built Quarry, Mine or Rig, the interim construction policy creates the required Machine instances and installed Part instances at 100% condition. The save then accumulates equivalent-full-load hours and intensity, computes Part wear with `industrial-wear-model-v1`, derives Machine condition from service slots, and excludes failed/offline Machines from extraction capability. There is still no procurement, repair or replacement UI. Demolition/rebuild creates a fresh fit-out but must retain existing occurrence reserve depletion and permanent terrain grading.

The extraction-function adapter must stop treating `machine-drill-machine` as universal. It should map the nine function keys in Section E to the listed Machine configuration IDs. Current Android method/building/depth restrictions remain unchanged. Exact power, workforce and output curves stay platform balance; the checked reference currently records Quarry `[4,9,17,29,46]`, Rig `[4,10,19,33,52]`, Mine `[5,12,23,40,64]`, Deep Mine `[7,16,31,54,86]`, and output `[10,18,30,48,72]` for L1–L5.

Machine art should be copied by `image.key` when generated. The three specialist Machines currently declare `not-generated`, so development bundles may use explicit presentation fallbacks; production art completeness remains a release gate, never a reason to replace their IDs locally. Approved canonical facts include stable IDs, relationship semantics, v1 wear rates and failure rules, fit-out quantities, extraction compatibility/depth boundaries, and the save-state ownership boundary. Most physical operating ratings and the existing provisional CC scenarios remain deliberately non-approved because no exact value was supplied by this review.
